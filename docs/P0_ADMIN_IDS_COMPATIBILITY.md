# P0 ADMIN_IDS COMPATIBILITY RISK
*Forensic Proof and Analysis*

## 1. Python Serialization
In the original Python implementation (`python_source/handlers.py`), `admin_ids` is accessed directly as a standard Python `list`:
```python
admin_ids = DB.get("ADMIN_IDS", [])
for aid in admin_ids:
    # iteration logic
```
When persisted to MongoDB/JSON, this list serializes natively as an array: `[123456, 78910]`.

## 2. Go Model Deserialization
In `internal/models/models.go`, the equivalent field is strongly typed as a Map for O(1) lookups:
```go
AdminIDs map[int64]struct{} `json:"admin_ids" bson:"admin_ids"`
```

## 3. The Decoding Failure (P0 Risk)
When `bson.Unmarshal()` attempts to decode the existing production document containing the array `[123456, 78910]`, it encounters a fatal type mismatch.
The exact error generated by `go.mongodb.org/mongo-driver/bson` is:
`error decoding key admin_ids: cannot decode array into a map[int64]struct {}`

**Impact**: 
1. The database load operation completely fails.
2. The bot fails to start against existing production data.
3. Access controls and states become inaccessible.

## 4. Required Solution
To ensure zero-destructive production cutover, we must introduce a **Custom BSON/JSON Unmarshaler Adapter** on the `BotState` object (or an intermediate alias). This adapter will intercept the raw BSON bytes, check if the field is an array or a map, and gracefully translate legacy array values into map keys before saving it to the active struct memory.
This guarantees existing production data is loaded perfectly, while all subsequent `$set` targeted updates from Go operate natively.
